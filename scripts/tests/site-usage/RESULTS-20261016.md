# 用户站点统计：2026-10-16 本机初测

结论：功能可全局关闭，持续字节计数热路径没有新增堆分配，但不是零 CPU 成本。已跑完 P/E 核、单核/四核、上传/下载 48 轮及额外 16 轮多核补测。共享主机干扰明显，合格的多核配对仍不足，不能据此声称无损或给出可靠的生产吞吐损耗率；保持默认关闭，待空闲窗口复测。

## 环境与方法

- Intel i7-13700，24 逻辑 CPU；sysfs 的 P 核 `0-15`、E 核 `16-23`。
- Linux `7.0.0-38-generic`、Go `1.26.0`，`CLK_TCK=100`。未改 governor、服务或其他进程亲和性。当前可见 cgroup 挂载没有暴露调用线程对应的 `cpu.max`，不能宣称已验证整棵层级不存在配额。
- 同一 Xray 二进制：`dc5f25e0223a8c9eef6aa0597a41edffe3a6d4b6790a2f51835faec56f64fcdb`。
- 原生工具：`d944af74387b80829584580cf48f60c0faf7812d7763fbcf5086129c87392d7b`。
- 无 TLS VLESS、32 个同用户连接、HTTP 嗅探得到固定 YouTube 分类。计费、嗅探、路由、stats API 和控制文件完全相同，只改采集 `0/1`。
- Xray、客户端、目标端分进程绑到不重叠的物理核心；两秒预热后测六秒，开启/关闭交错，各三次。上传以目标端确认的接收字节计量，下载以客户端接收计量。
- 保存逐核忙碌率、Xray CPU 时间、端点 CPU、采样峰值 RSS、站点计数开关验证。参见 [工具说明](README.md) 与 [全部原始记录](results/20261016.json)。

原筛选规则仅保留 P 四核下载和上传各一对。下载保留对为 94.74→85.47 Gbps（-9.8%），CPU 时间/GiB 为 343.6→355.8 ms；上传则是 92.76→108.40 Gbps。每组仅一对，且方向相反，不能把上传的正向变化当作功能收益，也不能把下载不利结果省略。E 四核仍没有合格配对。因此多核性能验收仍未完成，应在更安静且频率、温度可观测的环境增加样本。

## 微基准：成本位置

真实 mmap 计费计数与站点计数、开启门控、同一用户竞争；下表为三次中位数 ns/op。多核的 ns/op 是并发总操作的摊销墙钟时间，不等于单次调用的 CPU 时间，不能直接当网络吞吐。

| 计数场景 | 关闭 | 开启 | 新增堆分配 |
| --- | ---: | ---: | --- |
| P × 1 | 5.06 | 10.81 | 0 |
| E × 1 | 8.14 | 13.00 | 0 |
| P × 4，同用户热点 | 11.95 | 44.50 | 0 |
| E × 4，同用户热点 | 16.50 | 47.49 | 0 |

P 单核每条新连接的分类元数据准备约 49→537 ns，开启时 432 B、13 次分配；E 单核约 56→763 ns。同样不含网络建连、加密、其他已有分配以及首次用户/分类注册时的持久化。高连接建立率与大字节吞吐必须分别评估。类别扫描无需逐字节匹配，也不对每个数据块复制内容。

微基准期间主机也不是独占，且存在其他编译进程；这些数值用于定位和量级参考，不作为严格损耗率或低噪声基线。新连接关闭采集时保持原字节计数器，不创建站点包装器；已有启用连接在关闭后通过原子门控停止站点累加。
